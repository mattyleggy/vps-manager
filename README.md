# VPS Manager

Electron desktop app for managing one Ubuntu VPS over SSH: nginx sites and certificates, Docker, push-to-deploy from GitHub, and DNS records on Vultr.

```bash
npm install
npm start        # run the app
npm run dev      # run with auto-reload while editing
npm test         # unit tests (parser, review gate, action registry, chat loop)
npm run test:e2e # drives the real app against a fake server and a scripted model
python test/agent_test.py   # webhook agent tests
npm run dist     # build a Windows installer into dist/
```

## How it works

- **The app holds no server state.** Everything is read live over SSH (`ssh2`) each time a screen opens. Connect as `root` or a user with passwordless sudo.
- **Every operation is an action.** `src/main/actions.js` is the single registry: each entry has an id, a description, an input schema, review text and a handler. The UI buttons, the review dialog and the AI assistant all run actions through the same `runAction()` in `main.js`. To add a capability, add one entry there (and a button if you want one); the assistant picks it up automatically.
- **The assistant has two modes.** `src/main/chat.js` runs a Claude tool-use loop (`claude-opus-5-5`) whose tools are the registry's actions. In **Agent** mode (the default) those are all it can use. In **Server** mode (the switch above the message box) it may also use `server:command`, which runs any shell command it writes, so it can investigate and fix problems the built-in actions don't cover; every such command is still shown in the panel and runs only when you press Run, and ones that look destructive (rm -rf, reboot, stopping services, purging packages...) are flagged red. It lives in a side panel next to whichever screen is showing (toggle it from the top bar) and streams its replies. Its changes go through the same review gate as a button press: it says what it is about to do, shows the exact commands in the panel and asks whether to run them. It needs an Anthropic API key (Settings, stored encrypted) and sends your messages plus the server details needed to answer them to the Anthropic API; the webhook secret and SSH credentials are never sent.
- **Deployments.** This screen shows what is being deployed or built on the server at the moment, refreshing every 3 seconds while open (`activity:list`, `src/main/remote/activity.js`). It reads `/proc` in a single read-only scan. Deploy-agent runs (push or "Deploy now") are found through the `DEPLOY_PROJECT` variable the agent sets on every command it runs, so they need no agent change, and their live log can be followed. Docker builds, `compose up -d/--build/pull/build`, image pulls, git clone/pull, certbot, apt/dpkg and incoming scp/rsync are recognised by their command line, however they were started (including by hand over SSH); a command nested under another (the build inside a compose run) shows as that run's current step. Containers still starting, restarting or up for under a minute, are listed under it. Below that is the full deploy history (`activity:history`): every line the agent has appended to `history.jsonl` (never trimmed; the newest 5,000 are read), newest first, followed by a per-repository breakdown (deploys, succeeded/failed, last deploy, average time). Clicking a repository, or picking it in the list, shows only its deploys; projects that share a repository are grouped, and a removed project keeps its deploys under its own name. Logs older than the agent's newest 30 per project are marked as removed.
- **Nothing changes without review.** Every action that changes the server first shows a dialog listing what it will do and the exact commands (and file contents) it will run; only "Run" executes them. This is enforced in `src/main/ssh.js`, not the UI: a command not flagged `read: true` is refused unless it matches a step the user approved.
- **Site templates.** New sites come from templates in `src/main/remote/nginx.js`: Next.js, Laravel on a port (Docker / Octane), Laravel on PHP-FPM, a generic reverse proxy, and static files. For the port types the app picks the next free port (skipping listening ports, ports other nginx sites forward to, and ports published by any Docker container), and a site can get its Let's Encrypt certificate in the same reviewed step.
- **DNS is managed through the Vultr API.** With a Vultr API key saved in Settings (stored encrypted, sent only to api.vultr.com; `VULTR_API_KEY` in the environment also works), the DNS screen lists the zones on the account and their records, and adds, edits and deletes records. "Point DNS here" on a site (the `dns:point` action) creates or updates the A records for its domains with the server's address. These are API calls rather than SSH commands (`src/main/vultr.js`), but they go through the same review: the dialog shows the exact request before it is sent. Vultr only accepts the key from IP addresses allowed under Account → API → Access Control, and records only take effect for a domain whose nameservers are `ns1.vultr.com` and `ns2.vultr.com`; the DNS screen flags zones where they are not.
- **It lives in the tray.** By default the app starts with Windows minimised to the notification area, and closing the window keeps it running there (Quit is in the tray icon's menu). All three are switches under Settings → Windows. Only launches Windows makes at sign-in carry `--hidden`, so opening the app yourself always shows the window; a second launch brings the running one forward. Run from source (`npm start`), the startup entry is only written once you change one of those switches, so development copies don't add themselves to Windows startup.
- **nginx edits are guarded.** Every change is followed by `nginx -t`; on failure the previous file is restored and nginx is not reloaded. Old versions and "deleted" sites are kept in `/var/backups/vps-manager/nginx` on the server.
- **Site traffic.** "Traffic" on a Sites row or in the config editor opens Sites › name › Traffic (`nginx:traffic`, `src/main/remote/traffic.js`): requests per minute over the last hour, status classes, top paths and clients, and the latest requests with a filter, refreshed every 5 seconds from the site's access log. "Pin to menu" keeps the site under Sites in the side menu (saved per server in the local settings). A site without its own `access_log` writes to the shared log; the default "combined" format does not record the host, so the screen greps that log for the site's domains (mostly found in the Referer, so direct visits are missed), or shows the whole log. "Give it its own log" (`nginx:siteLog`) adds `access_log /var/log/nginx/sites/<name>.access.log;` to each server block and caps its size: `/etc/logrotate.d/vps-manager-site-<name>` rotates it past the chosen size (checked hourly from `/etc/cron.d`), keeping the chosen number of compressed old copies. The folder is separate because Ubuntu's own nginx logrotate entry already matches `/var/log/nginx/*.log`.
- **Configs are edited on their own page** (Sites › name) in the Monaco editor with nginx highlighting, directive and `$variable` completion, hover docs, a formatter and a quick lint for braces and missing semicolons. "Changes" diffs the editor against the file on the server, and lines `nginx -t` rejects are marked in place. "Write with AI" streams a new version of the file into the editor as Claude writes it (`src/main/nginx-ai.js`); it only produces text, and saving goes through the usual review. Unsaved edits are kept while the app is open.
- **Launch from GitHub is one flow.** The "Launch from GitHub" button (Auto-deploy and Sites screens; the `deploy:launch` action, so the assistant can do it too) takes a repo and a domain and, under a single review, adds the deploy project, optionally adds a read-only deploy key and the push webhook through the GitHub API (so later pushes redeploy), clones and deploys through the agent, creates and enables the nginx site (reverse proxy to a port, or static files from the checkout with dotfiles such as `.git` denied), and optionally gets a certificate. On that first clone the agent creates `.env` from the repo's `.env.example` and sets `APP_PORT` in it to the site's port (replacing the line, or adding it), so a compose file can publish `127.0.0.1:${APP_PORT}:…`; a `.env` that comes with the repository is left alone, and later deploys never touch `.env`. Steps stop at the first failure: a failed deploy never touches nginx. It needs the deploy agent installed.
- **Security › Repositories** lists every git checkout on the server (under `/opt`, `/srv`, `/var/www`, `/home`, `/root`, and every deploy project folder) with its origin, branch, last commit and uncommitted changes, and the known vulnerabilities in the dependency versions its lockfiles pin (`package-lock.json`, `yarn.lock`, `pnpm-lock.yaml`, `composer.lock`, `Pipfile.lock`, `poetry.lock`, `uv.lock`, `requirements*.txt`, `Cargo.lock`, `Gemfile.lock`, `go.mod`). The lockfiles are parsed on the server (`src/main/remote/security.js`, read-only) and the name/version pairs are checked against [OSV.dev](https://osv.dev) from this PC (`src/main/osv.js`; no key, nothing else is sent). Severity comes from the advisory, or from its CVSS vector. The result is cached until "Scan again". Credentials embedded in an origin URL are stripped on the server.
- **Security › Server patches** lists the apt updates waiting to be installed, security ones (from a `-security` pocket) first, with links to Ubuntu's notices for each source package, plus packages held or kept back, when the package lists were last refreshed, whether a reboot is pending (and the running vs newest kernel), and whether unattended-upgrades is on. "Refresh package lists" (`apt-get update`), "Install security updates" (`apt-get install --only-upgrade` for just those packages), "Install all updates" (`apt-get upgrade`, keeping your config files) and "Reboot server" are reviewed actions like any other.
- **Auto-deploy runs on the server, not in the app.** The Auto-deploy screen installs `src/agent/deploy-agent.py` as the systemd service `deploy-agent`:
  - config: `/etc/deploy-agent/config.json` (projects + webhook secret, root-only)
  - logs: `/var/log/deploy-agent/<project>/*.log`, history in `history.jsonl`
  - GitHub POSTs to `/hooks/github`; the agent verifies the `X-Hub-Signature-256` HMAC, matches repo + branch to a project, and runs its deploy command (default: `git pull --ff-only origin <branch> && docker compose up -d --build --remove-orphans`).
  - GitHub access, per repo: "Add deploy key" on a project generates `/root/.ssh/deploy_<project>_ed25519` on the server and adds its public half to that repo as a read-only deploy key through the GitHub API (`src/main/github.js`; needs a token in Settings with Administration: write on the repo). The agent pulls that project with its own key.
  - Repository list: the Launch from GitHub form lists your repositories. With a GitHub token it uses the API (private repos included). Without one it asks GitHub which account your SSH key belongs to (`src/main/github-ssh.js`, the same check as `ssh -T git@github.com`) and lists that account's public repositories; an SSH key cannot list private ones.
  - Webhook, automatically: saving a project with automatic deploys on adds the push webhook to its repo in the same reviewed step, when a GitHub token is saved (a token that cannot manage the repo's webhooks does not block the save; the app says why). On the Sites screen, a site whose deploy project has no webhook shows "No webhook" and an "Add webhook" button.
  - Webhook, per repo: "Add webhook" on a project creates the push webhook on that repo through the GitHub API with the agent's URL and secret (token needs Webhooks: write). If one already exists for the URL it is updated in place, which is how a rotated secret is re-sent.
  - GitHub access, shared fallback: one key at `/root/.ssh/github_deploy_ed25519`, wired into `/root/.ssh/config` for `github.com`, so deploy commands can run a plain `git pull`. Add its public half to GitHub as a deploy key (one repo, read-only) or to your account (all repos, not read-only).
  - App ports and `.env`: every project has a port (`app_port` in the config), chosen for you as the next free one when the project is added. The first clone creates `.env` from `.env.example` and sets `APP_PORT` to it. For a project cloned earlier, "Set up .env" on its row (the `deploy:env` action; `deploy-agent.py env <project>` on the server) does the same in one reviewed step, keeping every other value of an existing `.env`. "New site" offers the port of a project that has no site yet.
  - "Deploy now" in the app runs the exact same code path: `deploy-agent.py run <project>`.
  - Existing sites: "Auto-deploy" on a Sites row with no deploy project (the `deploy:detect` action, `src/main/remote/detect.js`, read-only) works out where the site comes from. A proxied port leads to the Docker container publishing it and its compose working dir, or to the non-Docker process listening on it and its working dir; a served folder is used as is. That folder is walked up to its git checkout, whose GitHub origin and branch are read. The project form then opens filled in, with a deploy command to match: the default for a compose app in its own folder, otherwise one that keeps the running compose project name, subfolder and `-f` files (so a deploy replaces the containers instead of starting a second copy), composer + artisan for Laravel on PHP-FPM, a plain pull for static files. Anything to check (not a checkout, not GitHub, uncommitted changes, a non-Docker app that needs a restart added) is shown above the form. Saving it is the normal reviewed project save, webhook included.

- **Terminal.** Ctrl+` (or the Terminal button in the top bar) opens an interactive shell on the server in a panel under the current screen, using the app's SSH connection (`term:*` in `main.js`, xterm.js in `views/terminal.js`). Hiding it keeps the shell running; Close ends it. What you type there is your own, so it does not go through the review gate.

## Layout

| Path | What |
| --- | --- |
| `src/main/` | Electron main process: SSH layer + review gate (`ssh.js`), action registry (`actions.js`), assistant (`chat.js`), settings |
| `src/main/github.js`, `src/main/vultr.js`, `src/main/osv.js` | The outside APIs the app calls: GitHub (deploy keys, webhooks, repo list), Vultr (DNS) and OSV.dev (known vulnerabilities) |
| `src/main/remote/` | One module per area: `system`, `nginx`, `docker`, `deploy`, `security` |
| `src/agent/` | The server-side webhook agent and its systemd unit |
| `src/renderer/` | UI (plain ES modules, no build step) |

Local settings live in `%APPDATA%\vps-manager\settings.json`; the SSH passphrase/password is encrypted with Windows DPAPI.
